# 自动化完成与人工负担：全局经验

更新：2026-09-28。适用于本工作区以减少人工操作为目标的识别、解析、核对和其他自动化任务。它是按需使用的工程经验，不新增审批、数据库、对象ID或验收平台，不覆盖用户当前任务边界。具体OCR案例不能变成页码、文字或坐标特例。

## 二、为什么最新一轮只完成两个对象

### 已完成的是“正确内容被软件卡住”

两对象的原色正文已有可用内容，但旧路径偏向处理后的候选；其中红章边缘还被误当正文截断。补原色完整正文核验后，已有内容得到支持。另外，显示字符串不变时未保存角色投影，组装会把独立章号重新混进地址；这是采用结果的下游错误，必须在最终API修复。

这证明一条重要规律：**已知正确输入没有走到完成出口时，继续增加候选或处理视图不会替代修调用链。** 同时不能反向推论“其他对象也已经识对，只需清问题”。

### 其余四个并不共享同一个直接故障

| 对象类型 | 本轮实际观察 | 尚未证明／未完成的事 |
|---|---|---|
| 污染地址 | 连续R通道主结果给出较完整地址，辅助在首字、内部字上有分歧；补主解码进入评分后仍未通过；去白边试验反而恶化首字 | 已有候选是否足以可靠裁决、哪个输入环节仍损伤区分信息；不能仅凭完整或高分采用，也不能把未通过视为不可读 |
| 混章表头 | 辅助为“原料全称”，主结果为“凉料的毛称” | 当前这次输入和识别没有给出可靠完整表头，不能从常见标签或词典补正确答案 |
| 两个记录框日期 | 一处为“2025年8月日”与“2025年3月6日”，另一处也有缺字与冲突 | 实际填写日期尚未恢复；事项正文通过不等于日期通过，不能借章年号补齐 |

这里的候选仅用于说明失败性质，不充当原件真值。

本轮把它们都归为“混章”是一种过粗的实现分组。按外观同类，不等于按阻断原因同类。一个原值确认样例通过，只足以推广到同样具备原值、范围和来源证据的对象，不能证明日期恢复或表头纠错路径也成立。

### 推进责任在于没有把困难恢复路径做完

- 完整裁剪解决的是“目标有没有进入输入”，不保证叠印下的内部笔画、缩放后小字仍可识别。
- 有限CTC评分解决的是“已有序列在该模型下得到多少支持”，不能凭空产生遗漏的正确文字，也不是字面正确概率。
- 同一通道变换没有收益，说明该方法失败；它既不证明原件不可读，也不免除改进输入或识别处理的责任。
- 缺少针对这类真实主OCR错误的新增独立验证，无法证明当前裁决已具备推广收益。旧安全回归增加到185项，不能补上这项效果证据。
- 实际执行仍以一轮有限试验加回归交付收尾，没有完成剩余四对象所需的恢复能力。应明确“未完成”，不能用“谨慎保留”包装成自动化任务完成。

## 三、之前反复出现的经验，落实为具体行为

| 已出现的失败 | 后续必须执行的行为 |
|---|---|
| 局部重识别把正确地址改坏；补前缀绕过资格检查 | 所有采用分支共用输入资格；按实际字形范围判断完整性；保留原值参与竞争，非空／更长／高分都不是覆盖理由 |
| 原始行存在，却被残余排序推到页尾或拆坏字段 | 先判断文字是否已经存在；纯组装问题复用原响应修区域、栏目与续行，不重新OCR；保存刷新走同一有效内容组装 |
| 历史差异反复阻塞；已采用结果仍和旧original比较 | 风险指向当前有效内容和明确来源；原始观察保留，已验证范围只解决对应风险；最终判定后不再重复生成同类问题 |
| 一个标点通过清整行；一段正文通过清整格 | 编辑位置、验证范围、完整对象三个概念分开；完整对象还需必要值、覆盖和归属完成；不通过拆分对象制造成功 |
| 整格黑像素、独立章号拖住完整正文 | 按真实文字对象核验正文、章文、日期和未归属墨迹；只在独立风险确实影响正文时阻止正文，原对象必需编号仍保留 |
| 完整章已验证，但原碎片没有解除入口 | 验证来源与显示替换范围分别记录；同页同章实际覆盖支持关联，不要求先把章文写进地址；框相交不足以清风险 |
| 辅助有候选却未评分；主新解码只有否决权 | 候选生成、有限评分和采用共用同一集合及位置；明确区分未评分、字表不支持和评分仍无法判定，不能全写“证据不足” |
| 红色分离丢字，符号“1”试验误通过 | 原色输入先行，变换必须证明针对的实际缺陷；文字模型对符号的置信输出不等于符号识别能力；未知不默填斜杠或空白 |
| 中间accepted与最终API不同；角色信息保存遗漏 | 首个正向样例必须追到最终正文、字段、来源及问题；检查重组装和持久化，字符串相等不代表元数据可忽略 |
| 合成大字全识对却被称为纠错验证 | 开发与留出分开，先验证字体实际渲染；包含真实主OCR识错但图像可读的样例；真值只在预测后评分 |
| 正常上传暴露重放未覆盖的漏报 | 重放验证采用逻辑；输入／触发／调用改变后另做必要真实上传，禁用结果替换；缓存权重与缓存结果分开说明 |
| 测试、候选和报告越来越多，人工对象几乎不减 | 按原对象完整完成数衡量收益；内容恢复、原值确认、覆盖关系解决分别统计，归并、显示和政策变化另列 |

## 四、下一次执行的最短闭环

不新建管理表或机制。在已有对象清单中完成以下信息即可：

1. **选一个因果上相同的类别。** 不以“都是红章”“都是低分”替代原因分类。对当前对象说明阻断处到底是输入、识别、候选、评分、归属还是结果落地。
2. **找最早失败点。** 没有可靠内容就修输入／恢复；内容已有但缺评分就补实际缺项；已验证却API未完成就修采用／组装／诊断。不要同时扩展几个没有完成出口的分支。
3. **一次改动对应一个可证伪假设。** 写清预期改变哪个输入或决定、什么结果说明方法无效；保留其他因素，避免同时换裁剪、颜色和评分而不知道什么起作用。
4. **先做一个贯穿产品的正向样例与相关反例。** 最终API完成对象，原始证据和其他风险不变，才推广同一机制。正确原值确认的成功不能充当错误内容恢复的成功。
5. **立即处理全部真正同类对象。** 输入与评分集合不变则复用响应；改变时只补必要调用，不重复无效处理，不按页面添加文字特例。
6. **检查最终结果并如实停在边界。** 代码固定后重放并做受影响真实产品验证；若方法失败，改变有理由的技术假设，而非无理由重试。若仍没有完成，应报告具体软件缺口及未执行项，不能宣称人工兜底已满足目标。

目前剩余四个不能继续作为一个恢复方法推广的集合：污染地址先定位完整候选为何未得到可靠支持；表头先解决混入图案下的实际文字恢复；记录框先取得完整填写日期及必要上下文，再验证日期。此处只确定因果顺序，不承诺现有权重必能达到目标，不授权新增模型或扩大业务范围。

## 五、人工核对边界与交付口径

仅当关键局部的输入、识别、必要评分和角色归属都实际处理过，仍不能可靠读取时，才可把该局部列为当前人工兜底。说明已做处理和剩余不确定；即使暂时需要人工，也不等于原件本身不可读。未实现代码、缺评分、错误裁剪、正确结果未进入API，继续标为软件责任。

不得为减少人工而解除姓名、编号、日期、限制词、未知符号等真实风险；也不得把原图可读却尚未恢复的内容永久归为用户责任。不改变业务阻塞政策；必要时政策讨论单列，不能计作OCR修复。

交付至少分清：完整自动完成、局部改善、实际纠错、误改、错误解除、过度拒绝和新增漏报。保留原对象身份；小样本零错误不代表生产零风险。报告不完整计时或缺失资源数据，不叠加重放／局部推理／正常上传为“全量重跑”。正常保存刷新不得触发OCR，人工修订和旧版本拒绝持续保护。

这些经验旨在减少绕路，不以新增阈值、白名单、冻结契约、哈希或更多拒绝条件执行。文档更新本身不计任何对象完成。
